## Confirmed Design Decisions (2026-05-27 update)

### Rule Selection — Three Rules Maximum
The system built across Chapters 3–8 uses exactly three rules, chosen to serve the teaching arc:
- **Rule 1 (Ch 4): Cash Threshold Structuring** — NRB-STRUCT-001. Rolling 30-day sum of cash deposits > USD 7,500 with ≥3 transactions. Introduces rule logic, scenario design, and the ATL/BTL framework.
- **Rule 2 (Ch 6): Transaction Velocity** — NRB-VELOC-001. >10 transactions in 7 days. Introduces a second detection dimension (frequency vs value) and the tuning/calibration methodology.
- **Rule 3 (Ch 7): High-Risk Country Counterparty** — NRB-HRC-001. Any transaction to a counterparty in a FATF/OFAC high-risk jurisdiction. Introduces network/counterparty data, closes a coverage gap, and provides a third ML feature type.

Extended exercises in Ch 6 and Ch 7 invite students to design additional rules — but the taught codebase is limited to three.

### Text–Exercise Continuum
Every chapter (3–8) must contain an inline code example in the **main body text** before the exercise. The exercise then explicitly extends that codebase. The structure for each chapter is:
1. Main text explains the concept and business context
2. A **Colab Preview** box in the text shows a simple, self-contained Python snippet illustrating the key idea
3. The exercise opens with a **Colab Extension** note pointing to the companion Colab notebook
4. The Colab notebook pre-loads the code from step 2 — students extend, not start from scratch

All code shown in the text and in Colab notebooks must be tested and valid.

## Platform

**Google Colab** — all exercises are cloud-based, browser-based, no local installation required.
- Students click a link and run in their browser
- Interactive UI elements use `ipywidgets` (equivalent to R Shiny, built inside Colab)
- No Python environment setup required

---

## Philosophy: Analytics-First, Not Python-First

Code in all Colab notebooks is **pre-written**. Students do not write code.

Students focus on:
- Running cells and interpreting outputs
- Understanding what the analytics are telling them
- Making risk-based decisions from analytical results
- Answering questions that require business judgment, not programming

**What exercises should NOT ask students to do:**
- Write Python functions or classes from scratch
- Debug code
- Configure libraries or environments
- Solve purely technical problems with no business interpretation

**What exercises SHOULD ask students to do:**
- "What does this alert pattern tell you about the customer's behaviour?"
- "Which customers would you prioritise for investigation and why?"
- "The threshold is currently $10,000. What happens to alert volume if you lower it to $8,000? Is that a good trade-off?"
- "Based on the ML scores, which alerts would you escalate? What is your rationale?"

## The SilverBank Synthetic Dataset

A single, coherent synthetic dataset called **SilverBank** runs through all exercises in Chapters 3–8.

The dataset is designed to:
- Be consistent across chapters (numbers tell a coherent story)
- Contain embedded suspicious patterns discoverable by the techniques in each chapter
- Support realistic alert volumes, investigation levels, and SAR decisions
- Be rich enough for meaningful analytics but simple enough to understand

**Core tables:**
- `sb_customers` — ~500 customers (retail and business, mix of risk ratings, geographies)
- `sb_accounts` — ~800 accounts (multiple types per customer)
- `sb_transactions` — ~30,000 transactions (12 months of data)
- `sb_counterparties` — ~300 counterparties (including high-risk jurisdictions)
- `sb_alerts` — generated progressively by student exercises (starts empty)
- `sb_cases` — generated by Chapter 8 investigation UI (starts empty)

**Embedded suspicious patterns (at least 8):**
1. Classic structuring (multiple transactions just under $10,000)
2. Rapid velocity (30+ transactions in 7 days)
3. High-risk country counterparties
4. Dormant account sudden reactivation
5. Round-dollar amounts
6. Shell company indicators
7. Smurfing (multiple accounts, same beneficial owner)
8. Layering (funds moving between accounts rapidly)

## Progressive System Build (Chapters 3–8)

| Chapter | What Gets Built |
|---------|----------------|
| Ch 3 | Seed system — explore SilverBank data; see what an alert, transaction, and investigation view look like |
| Ch 4 | First working rule: cash threshold >$10,000; alert generation; alert table; group customers by alert type |
| Ch 5 | Segmentation: K-Means peer groups applied to SilverBank customers; see how segmentation changes alert context |
| Ch 6 | Second rule: velocity (X transactions in Y days); threshold tuning exercise; extended exercise invites students to add their own rules |
| Ch 7 | Risk coverage mapping: students map the two rules against FFIEC red flags; identify gaps |
| Ch 8 | ML triage layer: unsupervised scoring ranks alerts by risk; full investigation UI with ipywidgets |

By the end of Chapter 8, students have built a complete, functioning transaction monitoring system.

## Chapter 8 Investigation UI (ipywidgets)

The investigation interface contains:
- **Alert queue view** — filterable by rule, date range, customer segment, ML risk score
- **Case detail view** — customer profile, transaction history, alert history, counterparty information
- **Disposition panel** — three buttons: Escalate to SAR / Close - No Action / Request More Info
- On Submit: writes disposition and rationale to `sb_cases` table
